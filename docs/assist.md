# 어시스트 화면 인식


## 이미지 인식

`scripts/vision/build_embedding_index.py`는 기존 기프트·이벤트 아트를 ImageNet 사전학습 MobileNetV3-small의 동일한 인코더로 576차원 벡터화한다. `--input`, `--output-index`, `--output-model`을 지정하며, 로컬 아트를 재사용하려면 `--gift-dir`와 `--event-dir`를 전달한다. 출력은 `public/models/assist-scene/visual-encoder.onnx`와 `embedding-index.json`이다. 기프트 투명 영역은 어두운 배경에 합성하고 이벤트는 화면과 대응하는 그림 영역을 사용한다. Worker 수정 후 `npm run build:assist-worker`로 배포 번들을 갱신한다.

화면은 로컬 Worker에서만 처리한다. 현재 장면 분류와 정해진 화면 영역의 이미지 임베딩을 함께 사용하고, 코사인 유사도 및 차순위와의 차이가 부족하면 후보를 내지 않는다. 후보는 3초 후 만료되며 획득·선택 기록은 사용자가 직접 처리한다. 같은 그림을 공유하는 이벤트는 복수 후보로 반환하고, 텍스트만 있는 선택지는 그림으로 식별하지 않는다. 벡터 검색은 브라우저의 로컬 인덱스에서 수행한다.

현재 검증 범위는 본인 영상의 16:9 화면이다. 같은 영상에서 조정한 185개 검수 프레임의 실제 Chrome Worker 결과는 이벤트 15/18 프레임, 보상 기프트 6/20 프레임의 10개 후보, 상점 구매창 2/22 프레임의 2개 후보였다. 수락한 그림은 원본과 일치했으며, 비이벤트 167개에서는 이벤트 후보가 없었고 보상·상점 이외 143개에서는 기프트 후보가 없었다. 독립 영상의 일반 정확도가 아니며 상점 목록의 작은 아이콘·다른 배치·검은 여백이 있는 캡처는 아직 보장하지 않는다. `scripts/vision/evaluate_visual_worker.mjs`로 실제 Worker를 다시 평가하며 프레임과 상세 평가 자료는 로컬에 보관한다.

## 화면 전체 OCR 보조 인식

이미지 인식과 별도로 Tesseract.js Worker가 3초 간격으로 화면 전체의 글자를 읽는다. 실행 중에는 프레임을 추가로 쌓지 않는다. 파일을 받는 곳은 다음과 같다(`features/assist/lib/model-assets.ts`).
- Worker 스크립트: 같은 출처(`/models/assist-*/…`). `npm run build:assist-ocr`·`build:assist-worker`가 만들고 일반 빌드에도 포함된다.
- 런타임(ONNX Runtime wasm·mjs, Tesseract 코어·언어 데이터): 같은 출처(`/models/assist-*/…`). 빌드가 `node_modules`에서 복사한다. 2026-10-16에 jsDelivr에서 받게 했다가 일부 브라우저에서 CSP가 그 스크립트를 막아 OCR이 시작되지 않아 되돌렸다.
- 인식 모델(`public/models`의 `.onnx`·`.json`)
  - 배포된 사이트는 Supabase Storage `limbus-assets/models/<버전>/`에서 받는다.
  - 로컬 개발 서버(localhost)는 `public/models`를 읽는다.
  - 자체 서버에는 저장소의 모델 파일도 함께 올라가지만, 접속 주소가 localhost가 아니면 쓰지 않는다(`.vercelignore`는 예전 Vercel 배포용이다). 화면·OCR 원문을 서버로 보내거나 기록하지 않는다.

읽은 글자는 기프트 이름, 이벤트 지문과 선택지 문구의 후보를 찾는 데만 사용한다. 짧은 일반 문구와 다른 이벤트가 공유하는 선택지는 보수적으로 제외한다. OCR 후보는 6초 후 만료되며 이미지 후보와 합치되 두 점수를 직접 비교하지 않는다. 획득과 선택 기록은 자동으로 변경하지 않는다. OCR 초기화에 실패해도 기존 이미지 인식은 계속된다.

## 인식 모드, 감지 설정, 합성·판매 (2026-09-24)

- **인식 모드:** `features/assist/lib/recognition-profile.ts`의 최고 성능·성능·밸런스·품질 네 단계다. 판정 규칙은 같고 읽는 양만 다르다. 이전 품질 설정이 기본값인 밸런스가 되었다. 품질은 밸런스와 같은 단일 패스를 더 자주 읽는다(장면 0.5초, 화면 1초/0.4초, 팝업 5장). 예전 품질의 2x2 겹침 타일(1.5배 확대, SAHI 방식 `tileGrid`/`mergeTileRects`)은 정지 화면은 조금 더 잘 읽었지만 한 번 읽는 데 2.4배 오래 걸려(약 800ms) 1초 안팎의 확인 창을 놓쳤다. 2026-09-24 재생 비교(새 품질/밸런스): 9/23 연속 합성 재료 17/17·17/17(예전 품질 14/17), 9/21 5칸 연속 9/11·9/11, 5/5 체인 7/7·6/7, 9/24 연속(PiP 가림) 27/30·27/30(예전 품질 26/30), 판매 5/5, 잘못된 변경 0.
- **감지 설정:** `features/assist/lib/detection-settings.ts`의 기프트, 테마팩·층, 선택지 이벤트 세 가지이며 기본값은 모두 켜짐이다. 끈 항목은 해당 OCR·아이콘 읽기 자체를 하지 않는다.
- **합성:** 판단 기준은 처리 시각이 아니라 프레임 캡처 시각이다. 연속 합성은 각각 따로 증거를 내고, 별의 가호로 약 0.3초 뒤 별도 팝업으로 돌아온 재료는 다시 획득한다.
- **판매:** `features/assist/lib/sell-evidence.ts`가 처리한다. 확인 창 문구에서 기프트와 가격을 읽고, 창을 띄우기 전과 닫은 뒤의 우측 상단 코스트("현재 ▸ 판매 후")를 비교해 판매와 취소를 구분한다.
- **스킬 교체:** 상점의 스킬 교체 창도 장면 분류기에서는 `shop`으로 잡힌다. `features/assist/lib/skill-exchange.ts`는 전체 화면 OCR에서 "[수감자] 스킬 교체" 제목과 "SKILL1x3" 보유 현황 세 줄을 읽는다. 플랜 모드에서는 PiP의 이번 층 기프트 위에 플랜 배분까지 필요한 교체(S1→S3 우선, S1→S2, S2→S3)를 표시한다. 창이 보이는 동안에는 판매 창과 같은 빠른 주기로 읽는다. 한국어 제목은 2026-09-21 영상 프레임 4장으로 확인했다. 영어와 일본어 제목 문구는 확인하지 못해서, 보유 현황 줄이 함께 읽힐 때만 인정한다.
- **런 시작 장면 라벨:** 장면 모델은 시작 기프트 화면을 `reward_choice`, 관측 화면을 `start_gift`, 확인 창 전반을 `sell`로 분류한다. 그래서 1층 시작 구간은 테마 선택 이후 장면(또는 0.8 이상의 `theme_select` 한 프레임)이 보일 때 끝난다.
- **인식 개선 샘플:** 사용자가 설정에서 참여를 켠 경우만 보낸다(`features/assist/lib/assist-samples.ts`). 어시스트가 읽는 동작마다(합성 한 번 `fusion`, 기프트 획득 창 `popup:<에피소드>`, 판매 `sale`) 프레임 그룹을 브라우저에 둔다. 300ms마다 한 장을 보고 화면이 바뀐 장면만 JPEG(1280px)로 담으며, 동작 직전 3장이 앞에 붙고 그룹당 최근 45장까지 남긴다. 제대로 읽으면 그룹을 버리고, 실패하면 뒤 3장을 붙여 올린다. 20초 동안 다시 보지 못한 그룹은 버린다. 올릴 때는 `/api/assist/samples`가 장마다 서명된 업로드를 내주고 브라우저가 비공개 버킷에 직접 올린다(버킷은 JPEG 400KB까지만 받음). 2026-10-02부터 동의문은 "인식 모델 학습에 사용"이고 삭제 기한을 약속하지 않는다. 동의 키가 v3이라 이전 참여자에게 다시 묻고, 새 동의로 보낸 샘플은 메타데이터에 `consent: 3`을 싣는다. `consent`가 없는 샘플(이전 문구 "180일 후 삭제"로 받은 것)만 받은 지 180일 뒤에 서버(`purgeExpired`)와 보관함(`pull_samples.ts`)에서 지운다(`sampleExpiresAt`). 공유 대상은 제한하지 않는다. 9/25~10/2 샘플 322건의 처음·중간·끝 프레임을 훑어보니 전체 화면 공유 세션 하나의 2건에만 게임 밖 화면(사이트 PiP 창, 방송 채널 목록)이 있었고, 동의문에 전체 화면 공유 안내를 넣었다.
- **획득 팝업 자리와 사전 해독 (2026-09-26):** 색 이름판은 1920×1080 게임 화면 기준 획득 팝업 자리(`POPUP_PLATE` 중심에서 110px 안, 폭 170~330px, 가로세로 1.8~2.45)에 있을 때만 읽는다(`acquisitionPlate`). 획득 팝업 샘플은 "기프트를 획득했습니다" 헤더를 읽었을 때만 올린다. GPU OCR은 이름판 줄을 기프트 이름 전체와 CTC 확률로 비교해(`ctcLexiconBest`, CRNN의 lexicon 해독) 1위가 2위보다 9 nat 이상 앞서고 greedy 경로보다 12 nat 이하로 모자라면 그 이름을 이름 읽기 하나로 더한다. 아이콘이나 다른 이름과 어긋나면 전처럼 판정을 보류한다.
- **영어·일본어 클라이언트 (2026-09-28):** 어시스트 설정의 게임 언어(한국어·English·日本語)가 OCR 인식 모델과 화면 문구를 고른다. 한국어는 `korean_PP-OCRv5_mobile_rec`, 영어는 `en_PP-OCRv5_mobile_rec`(7.8MB), 일본어는 `PP-OCRv6_small_rec`(21MB)를 쓰고 검출 모델은 공유한다(출처는 `public/models/assist-ocr/paddle/PROVENANCE.md`). PP-OCRv6 사전에는 한글이 없어서 한국어는 v5를 유지한다. 층·테마팩 선택, 획득 팝업 헤더, 합성 제목·질문·재료 칸 기준, 판매 확인 창, 스킬 교체 제목의 문구는 게임 현지화 파일(`../assets/data/{kr,en,jp}`)에서 가져왔고, 합성 창 기준 폭(`QUESTION_WIDTHS`, `TITLE_WIDTHS`)은 언어마다 다르다. 다른 언어의 이벤트·선택지 원문은 `/api/assist/texts/[lang]`에서 필요할 때 받는다. 모델과 문구는 유튜브 플레이 영상(영어 2편, 일본어 2편)의 0.5fps 프레임 OCR로 확인했고, 정답 라벨로 한 전체 재생 비교는 아직 없다.
- **층·테마팩 확정 (2026-09-28):** 새 층 지도는 1~2초만 보였다가 몇 분 뒤에 다시 나오는 일이 많아서, 같은 층·테마팩을 두 번 읽어야 확정하던 규칙에서는 층 기록이 그만큼 늦었다(9/24 한국어 녹화 3→4층 80초, 1→2층은 4분 뒤 다음 지도까지). 이제 배너 아래 줄이 테마팩 이름과 글자 그대로 같고 한 글자 차이 안에 다른 팩 이름이 없으면(`explorationThemeReads`의 `certain`), 층 숫자가 현재 층·다음 층이거나 앞선 판독과 같을 때 한 번에 확정한다. 한 글자 틀린 판독이나 `Line 2`처럼 숫자 하나 차이 팩은 전처럼 두 번 확인한다. 영어 배너는 검출기가 "Exploring"과 "Floor 3"을 따로 잡는 일이 많아 같은 높이의 박스를 한 줄로 합친 뒤(`joinRowLines`) 층을 읽고, 층 숫자 앞 문장부호("Exploring, Floor 3")도 무시한다. 일본어 팩 이름은 탁점·반탁점과 장음 부호를 빼고 대조한다("カジノブア" → カジノプアー). 재생 결과 층 기록은 배너가 처음 보인 뒤 1초 안이다: 한국어 1→2·2→3·3→4층, 영어 스피드런 1·2·3층(이전에는 1·3층 기록 안 됨).
- **인식 보고 (2026-09-26):** 같은 참여 동의로, 캡처 한 번마다 무작위 세션 ID를 만들고 획득 팝업·합성·판매를 읽었는지(`read`) 보류했는지(`held`) 센다(`features/assist/lib/assist-report.ts`). 실행 중 컴패니언의 자동 기록 밖에서 인벤토리가 바뀌면 직접 고친 기록(`add`/`remove`, 자동으로 넣은 기프트를 지우면 `auto: true`)으로 남긴다. 보고에는 그때의 캡처 크기(`width`, `height`)가 함께 실린다. 캡처 종료·페이지 이탈·15분마다 `/api/assist/reports`가 `limbus.assist_reports`에 넣고 180일 뒤 지운다. 샘플 메타데이터의 `session`이 같은 세션을 가리키므로 고친 기록을 샘플 라벨로 쓴다. 조회:

  ```sql
  -- 동작별 인식률(최근 7일)
  select a.key as action, sum((a.value->>'read')::int) as read, sum((a.value->>'held')::int) as held
  from limbus.assist_reports r, jsonb_each(r.counts) a
  where r.created_at > now() - interval '7 days' group by 1;
  -- 캡처 형태별 인식률: 정확히 16:9면 전체 화면, 그 밖은 창 모드로 본다(크기는 2026-09-27 이후 보고에만 있다)
  select case when r.meta->>'width' is null then '모름' when (r.meta->>'width')::int * 9 = (r.meta->>'height')::int * 16 then '16:9' else '창 모드·기타' end as capture,
    a.key as action, sum((a.value->>'read')::int) as read, sum((a.value->>'held')::int) as held
  from limbus.assist_reports r, jsonb_each(r.counts) a group by 1, 2 order by 1, 2;
  -- 직접 고친 기록: remove·auto=true는 오답, add는 누락
  select c->>'op' as op, (c->>'auto')::boolean as auto, count(*)
  from limbus.assist_reports r, jsonb_array_elements(r.corrections) c group by 1, 2;
  -- 샘플 라벨: 같은 세션에서 샘플 직후 60초 안에 고친 기프트
  select s.path, s.reason, c->>'op' as op, c->>'giftId' as gift
  from limbus.assist_samples s join limbus.assist_reports r on r.session::text = s.meta->>'session',
    jsonb_array_elements(r.corrections) c
  where (c->>'clientAt')::bigint between (s.meta->>'clientAt')::bigint and (s.meta->>'clientAt')::bigint + 60000;
  ```

**평가 도구:**

- `scripts/vision/replay_assist.mjs`: 영상 구간을 실제 어시스트 페이지에 화면 공유처럼 재생해 인벤토리 변화를 정답과 비교한다. `--slow ocr=<ms>,scene=<ms>`로 느린 기기를 흉내 낸다.
- `scripts/vision/bench_ocr_modes.ts`: 같은 프레임을 밸런스·품질로 읽어 앱 판정 함수로 채점한다.
- `scripts/vision/pull_samples.ts [out] [--delete-uploaded]`: 인식 개선 샘플(프레임과 `assist_samples` 행)과 인식 보고를 샘플 보관함(iCloud Drive의 `Limbus/assist/samples`: `<path>/<n>.jpg`, `rows.json`, `reports.json`)으로 내려받는다. 이미 받은 프레임은 건너뛰고, 그룹마다 프레임 크기 합이 올릴 때 기록한 `bytes`와 같은지 대조한다. 보관함에 있던 행은 유지하므로 서버에서 지워진 샘플도 남는다. 이전 동의 샘플은 180일이 지나면 보관함에서 지운다. `--delete-uploaded`를 주면 보관함에 온전히 있는 샘플을 서버에서 지운다(주지 않으면 서버에서는 아무것도 지우지 않는다). 아래 재생 도구와 학습 도구가 이 폴더를 읽는다.

**2026-09-28 느린 기기의 합성 누락:** 인식 보고(#268 이후 빌드)에서 합성은 55번 중 41번(75%)만 재료를 모두 읽었다. 보류 14건 중 11건이 "확인 창 없음"이었고 9건이 한 사용자(2560×1440, AMD GPU)에게서 나왔다. 올라온 프레임에는 확인 창이 재료까지 2~3장 찍혀 있었다. `replay_fusion_samples.ts`로 다시 읽으면 확인 창 14개 중 12개가 완성돼 판독 능력의 문제가 아니었다. 원인은 느린 기기에서 판독 차례가 밀리는 것이었다.

- 화면 OCR 한 줄을 전체 화면 판독과 탐험 배너 판독이 나눠 쓴다. 느린 기기에서는 배너 판독 한 번이 약 2초라, 합성 화면에서 전체 화면 판독이 10초 동안 한 번도 돌지 않았다. 이제 상점·합성·판매·스킬 교체 화면에서는 배너를 읽지 않는다. 배너는 지도에만 있다.
- 확인 창 없는 결과는 결과 직전의 휠 상태로 재료를 읽는다. 그런데 느린 기기는 결과 팝업을 3~4초 뒤에 판정하고, 그동안 결과 연출이 새 휠 상태를 쌓아 "최근 16개·4초" 보관에서 직전 상태가 밀려났다. 보관을 40개·8초로 늘렸다(640px 잘라낸 상태 하나 약 1MB, 합성 화면에서만 쌓임).

**2026-09-29 게임 원문 대조와 복구:**

- **서식 태그와 자리표시자:** 이벤트 지문·선택지·결과 원문의 Unity 태그(`<color=#ebcaa2>`, `<b>`, `<size=…>`, `<sprite …>`)가 정규화 뒤 `colorebcaa2` 같은 글자로 남아, 그 구간은 화면 글자와 절대 일치하지 않았다. `features/assist/lib/text-normalize.ts`의 `gameTextPieces`가 태그를 지우고 `{0}`(수감자 이름) 자리에서 원문을 나눈다. 이름이 들어가는 자리를 걸친 비교 창은 만들지 않는다.
- **일본어 OCR 유사 글자:** 탁점·반탁점·장음 부호를 빼고, 작은 가나와 모양이 같은 글자(力/カ, 口/ロ, 工/エ, シ/ツ, ソ/ン, 一/ー)를 양쪽에서 같은 글자로 접는다(`ocrNormalized`). 이벤트·선택지·기프트 이름, 획득 팝업 이름판, 판매 창 이름에 쓴다. 획득 헤더 판정은 그대로다.
- **두 단 화면:** 검출 줄을 위에서 아래로 이으면 이벤트 지문 줄 사이에 오른쪽 선택지 줄이 끼어든다. `columnText`가 같은 왼쪽 끝으로 이어지는 줄을 단락으로 모아 원래 읽기 순서 뒤에 덧붙인다(`|`로 구분, 비교 창은 넘지 않는다).
- **판매 이름:** 한 글자 차이 이름은 5글자 이상이고 다른 모든 이름과 3글자 이상 떨어질 때만 인정한다(획득 팝업과 같은 `nearestName`). 판매는 이후 코스트 증가로 한 번 더 확인된다.
- **복구:** GPU OCR이 실행 오류나 8초 시간 초과를 한 번 내면 캡처가 끝날 때까지 Tesseract만 썼다. 이제 10초·45초·3분 뒤 다시 불러오고, 5분 이상 정상 동작한 뒤의 실패는 대기를 처음부터 센다. 전체 화면 OCR 요청의 오류는 그 프레임만 건너뛰고 3회 연속일 때 레인을 정리하며, 레인이 모두 없으면 5초·20초·60초 뒤 워커를 다시 만든다(예전에는 워커 하나일 때 OCR이 캡처 끝까지 꺼졌다). 장면 워커는 준비된 뒤 추론 5회 연속 실패에서만 캡처를 끝낸다(예전에는 한 번에 화면 공유 전체가 끝났다).
- **메인 스레드:** 카탈로그 비교 색인을 카탈로그마다 한 번 만들고(읽기마다 재구성하던 것), 실행 화면의 층 패널을 memo로 감싸 캡처 상태 갱신마다 다시 그리지 않는다. OCR 워커는 줄마다 캔버스를 새로 만들지 않는다.

**2026-10-06 결과가 잔영인 합성, 합성 실패 샘플의 판독 진단:**

- **잔영 결과:** 잔영은 여러 개를 가질 수 있어 자동 기록하지 않는다. 결과 팝업이 잔영이면 팝업을 통째로 건너뛰어 그 합성의 재료도 인벤토리에 남았다. 이제 잔영은 기록하지 않고 확인된 재료 중 인벤토리에 있는 기프트만 한 번의 기록으로 뺀다(`CRAFT_FUSION`의 `resultId: null`). 합성 증거가 팝업보다 늦게 와도 같다. 재료가 잔영뿐이면 아무것도 바뀌지 않는다. 알림은 "합성 반영: (잔영 이름) 합성, 재료 N개 제거"다. 리듀서는 단위 테스트로 확인했고, 실행 화면에서 결과가 잔영인 실제 합성으로는 확인하지 못했다(그런 구간이 있는 녹화의 정답 파일이 없다).
- **판독 진단:** 재료를 다 읽지 못한 합성의 샘플 메타데이터에 `diagnosis`(600자 이내)를 싣는다. `fusionDiagnosis`가 만들며 형식은 `v1;d=<확인 창 없이 만든 합성 1/0>;n=<N>/<M>;u=<칸 수 미정 1/0>;ref=<휠 모양을 아는지 1/0>;kept=<보관한 휠 상태 수>;res=<첫 프레임에서 결과 팝업까지 ms 또는 ->` 뒤에 읽은 상태를 시간순으로 `|<w 휠·d 확인 창><첫 프레임 기준 ms>:<칸>,…`로 잇는다. 칸은 `id@점수/격차`, `_`(빈 칸), `-`(못 읽음)이다. 화면 내용은 들어가지 않는다. 운영 샘플이 모이면 `candidates`가 빈 합성에서 휠 상태를 몇 개 읽었고 무엇으로 읽혔는지 본다:

  ```sql
  select created_at, meta->>'width' w, meta->>'height' h, meta->>'diagnosis' from limbus.assist_samples
  where reason like 'fusion%' and meta ? 'diagnosis' order by created_at desc;
  ```

## 편성 안내, 합성 순서 (2026-10-22)

- **편성 화면**: 장면이 `run_setup`(또는 시작 단계가 끝난 뒤의 `battle_setup`)이면 PiP에 수감자 순서대로 실행 편성의 인격 얼굴과 편성 번호를 보이고, 편성 코드 복사 버튼을 둔다(`CompanionFormation`). `FORMATION_SCENES`(run_setup·battle_setup)이면 런 시작 단계에서도 편성을 보인다. 2026-10-23 녹화를 0.5초마다 판독해 보니 지금 순서는 던전 입장(run_setup) → 편성(battle_setup) → 별의 가호 → 시작 기프트(gift_acquired·start_gift) → 관측(start_gift)이었고, 시작 기프트 화면이 battle_setup으로 읽힌 적은 없었다.
- **별의 가호 화면**: 2026-10 화면은 파란 카드라 장면 모델(준비 화면 학습 사진 14장, 모두 옛 빨간 화면)이 놓친다. OCR이 "별의 가호"와 "입장"을 한 번에 읽으면 4초 동안 `start_gift`(`BLESSING_SCENE`)로 둔다(`features/assist/lib/blessing-screen.ts`). 처음에는 `run_setup`으로 두었는데, 별의 가호가 편성 다음에 오면서 편성이 끝난 뒤에도 PiP에 편성이 다시 뜨고 4초를 더 남았다(2026-10-23 수정). 새 화면 녹화를 받으면 장면 모델에 넣어 다시 학습한다.
- **테마팩 클리어 보너스** (2026-11-05): 테마팩 선택 화면에서 카드마다 아래 CLEAR BONUS 줄의 기프트를 1초마다 읽는다(`features/assist/lib/clear-bonus.ts`, 워커 `clear-bonus`). 그 층 보스를 이기면 이 중 1개(노말), 하드 이상은 2개를 고른다. 카드는 1920×1080 UI에서 x 964를 가운데로 315.8 간격의 고정 자리(3·5장은 홀수 자리, 4장은 짝수 자리)에 서고, 줄 위쪽 1픽셀 선(y 807, 노말 파랑·하드 빨강)이 있는 자리만 본다. 아이콘은 카드 가운데 기준 65.2 간격, 중심 y 843.6, 한 변 64.9; 반 칸씩 일곱 자리를 아이콘 분류기로 읽고 강한 판독이 많은 배치(4·3·2·1개)를 고른다. 두 번 연달아 같으면 둔다. 팩 이름은 같은 화면 OCR의 카드 이름 줄(y 640~730)로 카드와 묶고, 이름이 없으면 기프트가 모두 그 팩 풀 안인 카드가 하나뿐일 때 그 카드로 본다. 고른 팩이 정해지면 그 층 기록(`floorLogs[].clearBonus`)에 넣고, PiP 층 화면에 클리어 보너스 줄과 "상점에서 사지 않아도 돼요" 안내(계획 기프트가 고를 수 있는 수보다 많으면 나머지는 사라는 안내), 기프트 칸에 "클리어 보너스" 표시를 단다. 선택 화면에서는 계획 기프트가 클리어 보너스에 있는 카드를 보여 준다. 검증: 라벨 붙은 표본 350장(1280×720·1366×768·1440×1080·1920×1080) 원본과 1280 JPEG 75 모두 349장 정확, 1장 하나 모자람, 틀린 판독 0. 실제 녹화(하드, 빨간 선)에서도 읽히는 것을 눈으로 확인했다(정답 라벨 없음).
- **합성 순서**(`fusionGuide`): 지금 만들 수 있는 조합을 최종 기프트, 최종 레시피 재료, 몰입 키워드, 그 외(등급 순)로 두고, 재료 1개가 모자란 최종 기프트를 따로 보인다. 런 현황과 PiP 합성 화면이 같이 쓴다.
- **기프트 추천은 뺐다**(2026-10-23): 상점·보상·이벤트 화면에 읽힌 기프트를 점수로 골라 보이던 추천 줄과 공개 플랜 기프트 통계 API를 지웠다. 화면에 보인 것 중에서 고르다 보니 초보자가 플랜과 상관없는 기프트를 추천으로 오해했다.
- **플랜 층 메모**(2026-10-23, `CompanionPlanMemo`): 플랜으로 시작한 런의 PiP 층 화면과 시작 기프트 화면에 그 층의 플랜 메모를 최대 3줄로 보인다. `noteLabelPreview`가 메모를 한 줄로 펴면서 기프트 블록(블록 문서의 `noteAsset`, 글 메모의 `{{gift:…}}`)을 `[g:이름]`으로 바꾸고, 플랜 카드와 같은 `NoteRenderer giftLabel`이 기프트 라벨로 그린다. 스킬·패시브 카드와 영상·표는 뺀다.
